# AgentScroll 系统设计与内容规则

本文描述 AgentScroll 如何把互联网内容转化为可供 AI 学习和分享的信息，以及支撑这些流程的系统边界和平台采集方式。配置、接口、字段、平台支持与测试命令见[使用与接口](usage.md)。

## 业务目标

AgentScroll 让 AI 持续了解近期真实发生的热点、新闻、知识和网络表达，用于后续对话中的背景认知和即时分享。业务判断同时考虑：

- 真实性：知识、新闻来自实际读取的正文或评论。
- 趣味性：优先保留值得聊、好玩、抽象或能体现网络语境的内容。
- 成本：限制候选量、正文规模、模型调用次数、模型发送上下文大小，适应高频定时执行。

当前有两条主要入口：围绕指定主题主动搜索，以及从热榜中筛选值得学习的内容。

## 技术边界

### 模块依赖

依赖方向保持单向：collector 不依赖模型运行时，prompts 不执行 I/O，workflows 可以组合 collector 与 inference。

中文相关性排序使用 `jieba` 分词和词性；仅在分词没有共同词时使用字符 bigram 兜底。

### 推理代码维护

`agentscroll/inference/` 是从 WeClone 推理模块同步到本仓库的源码快照，使用 AgentScroll 不需要额外克隆 WeClone。

同步由 `.github/workflows/sync-weclone-inference.yml` 负责，只在 GitHub Actions 中手动触发。`__init__.py`、`audit.py` 和 `llm_client.py` 是本仓库保留的通用推理基础设施覆盖层，`online_infer.py` 不再同步；其余文件检测到上游变化时更新快照并创建 PR。

### 运行产物

| 路径 | 内容 |
| --- | --- |
| `outputs/agentscroll.sqlite3` | 热点、标题缓存和分享任务状态 |
| `outputs/hotlists/` | 热榜 JSON 快照和标题 TXT |
| `outputs/knowledge/` | 搜索知识文件和热点知识卡 |
| `outputs/shares/` | 即时分享 review 产物 |
| `outputs/logs/` | 运行与推理日志 |
| `outputs/test_artifacts/` | 真实平台测试证据 |

数据转换默认创建新文件，不覆盖输入；同一批次的关联产物使用一致名称，避免 JSON、TXT 和分享结果错配。

## 目标处理链路

目标链路为：信息源 → 采集 → 统一格式 → 持久化 → 去重、聚类与时序统计 → 兴趣过滤、打分与 Top-K → 补充正文、评论和相关报道 → LLM 分析与汇总 → Briefing 或推送。

其中聚类、完整兴趣建模和日报属于后续设计方向，不能仅凭本图视为当前已经实现。当前公开行为以以下两条流程和[使用与接口](usage.md)为准。

## 主动搜索

### 场景路由

主题搜索支持三种场景：

- `formal`：面向公告、政策、报告、研究、新闻进展和正式分析，优先使用知乎、微信公众号和今日头条。
- `informal`：面向网络梗、流行语、二创、吐槽和评论区语境，默认使用微博、B站和抖音。小红书当前不进入默认路由，但仍可显式指定。
- `auto`：根据查询意图选择路线；没有明显信号的短主题词优先发现非正式语境，较长且信息明确的查询优先走正式场景。

用户显式指定平台时，以指定平台为准，不再应用默认场景路由。“正式”和“非正式”描述内容形态，不代表来源可信度；自媒体内容、未确认消息和网友说法仍需保留来源限定。

### 搜索规模

`quick`、`default` 和 `deep` 分别把每个平台的候选上限设为 5、10 和 20。B站对应最多搜索一、二、三页；小红书在 `quick` 模式使用公开索引发现候选，在 `default` 和 `deep` 模式优先使用 Playwright。其他平台沿用各自采集路径并按档位调整候选规模。

无论选择哪一档，命中的候选都会继续读取正文；支持评论采集的平台还会读取评论。同一平台的详情请求按配置区间限速，不同平台可以并发。

### 内容读取

搜索结果只是候选入口。候选必须继续读取详情，获得真实正文或发布文案；需要评论时还要读取真实评论。

只有摘要、正文为空、正文过短或缺少有效原文地址的候选不进入最终知识。视频平台的正文指发布者文案或完整简介，不包含自动推断的字幕和音视频转写。

微博、小红书、B站、抖音、微信公众号和今日头条只保留成功读取到正文或发布文案的条目。统一详情校验要求正文去除首尾空白后至少有 2 个字符，并且正文类型、解析来源和正文地址有效；详情受阻、只有摘要或正文为空的候选会被丢弃。微信公众号和今日头条使用通用文章提取器时，可识别的正文块至少需要 40 个字符；未命中正文块时，段落兜底结果至少需要 80 个字符。知乎文章和回答的详情正文少于 20 个字符时视为不可读。支持评论采集的平台按配置上限保留有文字的评论，且不保存评论作者。

### 平台采集路径

以下描述的是当前代码中的读取路径，不等同于本轮已经验证平台在线可用：

- 微博：`mcp-server-weibo` 获取访客 Cookie；正文通过 MCP 单帖详情读取，评论通过微博评论 API 读取。
- 小红书：Playwright/XHR 与站外 URL 发现；正文优先读取页面初始状态中的笔记描述，专用正文 DOM 作为后备；评论从详情页签名响应提取。
- B站：公开搜索 API 与 Playwright 兜底；视频详情 API 读取完整简介，reply API 读取评论。
- 知乎：站外发现公开 URL，随后用 Playwright 读取正文，并按内容类型访问评论 API。
- 抖音：Playwright 与站外 URL 发现；正文读取分享页路由数据，专用正文 DOM 作为后备；评论从移动分享评论 API 提取。公开分享页出现 WAF challenge 时使用移动 Chromium 完成挑战并读取路由数据，不退回到 meta description。
- 微信公众号：搜狗微信搜索后访问文章页，只读取文章正文，不读取精选留言。
- 今日头条：服务端搜索页、热榜与站外 URL 发现；正文来自移动详情页或来源页，评论来自文章页签名响应。

### 知识沉淀

一次搜索把不同平台的有效内容合并成一份可追溯元数据和一份面向模型的紧凑知识文本。

- 每条内容保留平台、发布时间、正文、原文 URL、非零互动量和最多 10 个标签。
- 正文按配置上限保留；换行压缩为空格，超长内容按段落或句子边界截断并标明原始字符数。
- 评论去重后按点赞数降序保留最多 10 条；同赞数保持平台原顺序。
- 已知发布时间的内容按时间升序排列；无法确定时间的内容放在已知日期内容之前。
- 作者、平台内部 ID、图片、相关性解释、抓取状态、解析路径和 DOM 证据不写入 TXT。
- 正文为空或没有有效原文 URL 的条目不进入知识文件；微博的“图片评论”“转发微博”等无正文占位评论会被过滤。

具体文件、返回字段和可调上限见[返回值与知识文件](usage.md#返回值与知识文件)。

## 热榜学习

### 拉取与去重

热榜按业务类别组织。Agent 没有指定类别时使用“综合”组，依次包含微博、虎扑、百度贴吧和知乎。

拉榜阶段只生成索引，不读取正文或评论。不同榜单合并后按 Source ID 和榜单排名保留最先出现的条目，再按 URL 或标题全局去重。URL 规范化会统一协议和域名大小写、移除 fragment 并保留 query；标题规范化会统一 Unicode 兼容字符、大小写和连续空白。完整平台目录、Source ID 和快照格式见[NewsNow 热榜](usage.md#newsnow-热榜)。

### 第一轮筛选

模型只依据当前热榜快照选择值得继续处理的话题，不在第一轮打开 URL 或搜索互联网。目标分为：

- `news`：刚发生或正在发展，并具有现实公共价值、可能影响较多人的新闻与变化。
- `fun`：新词、固定表达、梗、反差、抽象或具有即时分享价值的内容；影视宣传、明星宣传不属于 `fun`。

兴趣相关性与 `news`、`fun` 正交，不增加第三种类别。用户只配置一组兴趣关键词，每个词可以是具体词、人物、产品或领域的语义锚点。明确相关的领域动态即使受众较窄也可提高筛选优先级，用户被视为熟悉对应领域及其术语和圈内梗。普通宣传、常规动态、旧闻、重复进展、语义不明内容或擦边提及不能因为兴趣关键词而入选。重大新闻和高趣味内容不需要与兴趣关键词相关，兴趣相关内容也不占固定名额。

最多选择 15 个话题，实际数量由符合条件的话题决定，不要求 `news` 与 `fun` 的数量均衡。筛选前先按标题规范化规则排除近期已经成功判断过的完全相同标题；若没有新标题则跳过模型请求并正常返回空话题。候选保留其在当前热榜中的整数 ID；模型只返回 ID，程序校验后再映射回标题和来源。属于同一事件的多个标题合并为一个代表话题，避免重复占用名额。

标题准入不以热度本身为依据。普通个人纠纷或家庭矛盾、无法辨认具体主体或对象的泛化标题、普通家庭或明星日常动态不进入后续采集，除非标题已经明确呈现异常后果、较广公共影响、新梗、可复用表达、反差或荒诞点；影视宣传、明星宣传仍不属于 `fun`。语义不明本身不是趣味价值，只有陌生短语本身具有新词、黑话或固定表达特征时才作为待查线索，不能因为缺少主体、对象或视频上下文而选入。

跨批次事件判断不额外生成摘要或 signature。程序先用 `jieba` 词性分词对标题做本地匹配，名词、人名、地名和机构名等名词类词权重更高；没有共同词时才用字符 bigram 兜底。若当前标题与最近 6 小时的历史标题包含相同明确人物名，即使普通标题相似度未达到召回阈值，也把该历史事件作为疑似候选并优先排列。当前标题没有明确指向另一件事时，第一轮优先按 `update` 交给后续材料核验，不因标题省略动作或上下文而直接新建事件；标题明确指向不同对象或事件时仍按 `new` 处理。每个当前标题最多召回 3 个历史事件候选，不对所有召回标题的合计字符数设置额外上限。第一轮模型请求同时把候选判断为 `new`、需要核验进展的 `update` 或没有实质新进展的 `seen`：`seen` 不进入采集，`new` 和 `update` 继续生成知识卡。

跨轮次状态统一保存在一个本地 SQLite 数据库。第一轮结果成功校验后，本轮所有标题都会写入标题缓存，包括入选、未入选、`seen` 和此前精确命中的标题；缓存只表示已经分析过，不承担事件状态。热点记录同时保存稳定身份和当前有效知识，`new` 在本轮结果确定后创建记录，`update` 在同一记录上更新当前知识；复杂的标题链和更新链保留在记录的 JSON payload 中。证据、采集尝试、筛选结果和知识卡批次仍按轮次写入文件供 review，不进入数据库，也不作为后续状态恢复来源。

标题筛选完成后立即保存独立 JSON，再进入正文采集；因此后续采集或知识卡生成失败时，仍可检查本轮选中的代表标题、平台、类别、模型初步判断的兴趣关键词和关联标题。修改兴趣关键词只影响后续未命中标题缓存的条目，近 7 天内已经分析过的相同标题不自动重筛。

模型先从当前热榜标题中找出属于同一事件的条目，并保留模型选出的代表标题用于描述本轮话题。正文采集独立选择非知乎入口；只有整组标题全部来自知乎时，卡片阶段才用一次批量模型请求把该组标题转换成 2 至 3 个短检索词，再到微博搜索具体帖子。系统不读取知乎正文或地址，知乎标题只作为待验证的话题线索，不能单独支持知识卡或分享。

程序默认以取得 3 个可读入口为目标，先尝试模型已识别的非知乎关联条目；不足时，纯知乎话题使用上述检索词，其他话题直接复用已有非知乎标题，仅到微博补采。虎扑和贴吧仍沿已有非知乎热榜入口下钻。最终只保留热榜快照日期及其之前连续 7 个自然日内、发布时间能够确认的帖子，同一帖子被多个检索词命中时只保留一次。某个入口失败、日期缺失或超出范围时继续尝试后续入口；微博补采后仍不足 3 条，则不直接成卡，最后才转入有限主动搜索。
仅有热榜标题、搜索摘要或失效地址时，不把话题标记为证据完整。

采集选中内容时，微博通过 `mcp-server-weibo` 定位 feed；虎扑读取帖子结构化数据；贴吧通过话题页和 Playwright 读取帖子与楼层；显式选择 Bilibili 热榜时，通过热搜标题定位视频并读取简介和评论。

### 知识卡与补搜

每个话题分别请求模型完成材料判断、知识卡生成和分享编排；多个话题并发处理，结果按话题 ID 汇总，并共同写入本轮 review 批次，当前有效状态写入 SQLite。单个话题请求失败或返回结果未通过校验时，该话题保留为 `needs_research` 并记录错误，不中断其他话题的生成、合并和落盘。知识卡模拟真人对近期谈资的简短记忆，只保留“有这么个事或梗”、大致意思和一至两个值得记住的信息点，不整理完整报道。每次请求使用共同的状态、评分、输出和来源规则，再只附加当前 `news` 或 `fun` 类别的专用判断与写作规则：

- `complete`：现有证据足以辨认基本事件或梗；即使精确数字、完整经过或各方回应不全，也可保留来源限定后生成简短知识卡。带有兴趣关键词的话题，只要正文能确认领域内存在具体、近期的实际变化，就不因受众较窄而淘汰。
- `needs_research`：未达到正文采集目标，或连基本事件、梗或有趣之处都无法辨认，需要有限补搜。
- `rejected`：证据已能确认话题是旧闻回顾、没有近期具体进展、不具现实公共价值、已经过时或与标题不符；不生成知识内容，也不进入分享和补搜。

`new` 生成新卡；`update` 的模型输入补充当前知识的标题、知识、聊天语境、上次更新摘要，以及当前 7 天窗口内按时间从旧到新排列的成功更新标题。标题链只包含每次 `complete update` 的代表标题和同话题标题，不含证据、搜索结果或 `seen` 标题，只用于识别重复进展，不能作为事实证据。更新证据明确支持新进展时，模型以原 `knowledge` 为底稿生成合并后的当前状态：保留仍成立且对理解核心事件有用的信息，直接替换已过时的数字或结果，局部细节只在仍具核心价值时保留；`latest_update` 只描述本轮新增内容。程序更新同一热点记录并替换单个 `latest_update`，同时在 JSON payload 的 `updates` 中追加本次更新标题、合并后的知识快照、增量摘要和分享评分。首轮没有证明新进展时进入补搜，补搜后仍只有旧内容则只记录本轮失败状态，当前有效知识保持不变，也不追加更新记录。

补搜只处理 `needs_research`，复用 `agentscroll search` 的平台采集入口读取真实正文以及支持平台的评论：`news` 搜微博、微信公众号和今日头条，`fun` 只搜微博，每个话题合计最多保留 3 条可读内容。3 条限额在详情和评论请求前按平台顺序尽量均分，因此 `news` 为 1/1/1，`fun` 的 3 条额度都给微博。多个补搜话题并发处理，不重新处理 `complete` 或 `rejected`，不直接使用 Bing、DuckDuckGo 摘要，也不启用 Codex 原生 Web Search。若第一轮与主动补搜都没有取得任何可读正文，话题直接保留为 `needs_research`，不再调用知识卡模型。补搜只需让人知道话题大致在说什么，不做穷尽式事实核验；未确认新闻或指控必须保留“网传”“帖子称”等限定。

### 即时分享

模型在同一次知识卡请求中分别生成大众视角的 `general_share_score` 和兴趣视角的 `interest_share_score`。大众分沿用 0 或 1 至 4 分标准；兴趣分只针对标题阶段给出的候选兴趣关键词，范围为 0 或 1 至 3.9 分。弱关联、普通提及或过时内容为 1 至 2 分，直接相关但不值得主动发送的常规变化为 2 至 3 分，只有具体、近期、值得兴趣用户主动知道或讨论的内容才能达到 3 至 3.9 分。程序取两项的较高值作为最终 `share_score`，只将达到 3 分的话题放入分享队列；兴趣本身不能产生 4 分。非 `complete` 状态或没有可用来源时两项均为 0。

两项评分在 `update` 中都只评价相对于旧卡的新增进展。默认最高为 2.9；只有新增内容足以明显改变事件的核心状态、结果或影响，并值得再次主动告诉已经知道该事件的人时，才可达到 3 分，大众分的 4 分只用于新增进展本身构成重大转折或产生广泛影响的情况。普通数字变化、原因或背景补充、现场细节和重复回应不重复分享。标题阶段直接确定候选兴趣关键词，知识卡模型只依据正文评价其分享价值，不再重复返回关键词。

知识卡最终结果在落库前仍是暂定结果。原关系为 `new` 且大众分达到已启用分享策略的 `immediate_score` 时，程序使用本轮已经采集的正文和来源标题，与最近 7 天同类别完整历史事件的标题、当前 `knowledge` 和 `latest_update` 做一次本地高置信匹配；匹配同时要求足够的历史信息覆盖、多个共同关键词，并且最佳候选明显高于次优候选。只有兴趣分达到阈值不会触发该复核。没有命中时直接保留原结果；命中时把该话题改为 `update`，补入 `previous_card` 和 `timeline`，复用现有证据单独重评一次，不重新搜索。只有重评结果会写入热点状态和分享批次；重评失败时保留为 `needs_research`，不会回退发送第一次的即时分享结果。最终保存的分享文案和实际使用的来源标题会作为后续本地召回别名，但不进入成功更新时间线。

分享 review JSON 保留候选内容、两项评分、最终分和标题阶段判断的兴趣关键词；实际分享时先发送大致内容或标题和真实原文地址，再把评论原文单独发送一条，不添加“网友评论”或“我的评论”前缀。`news` 的原标题准确、自洽且本身有吸引力时直接用作分享文案；标题含义不明、问句过长或容易误导时才改写。标题末尾“如何评价”“怎么看”“如何解读”等不提供事件信息的讨论性问句应删除或改写为陈述句，承载核心事件信息的问句可以保留。改写时保留原标题中最有传播力的真实表达，只补一个材料明确支持的关键信息点，不写成新闻摘要。`fun` 直接使用原标题，不改写或补充分享文案；大众分仍要求普通人能直接理解，兴趣分可以按熟悉对应领域的用户判断。两类都不伪造悬念或隐去改变内容性质的关键事实：

- 模型选择真实评论时只返回当前话题内唯一的本地评论 ID，由程序从证据回填；评论可以来自该话题的任一已采集帖子，不要求属于分享来源。
- `news` 优先选择已提供内容最直接、完整地支持分享文案和最新进展的来源；`fun` 优先选择已提供内容最能呈现笑点、反差或抽象内容的来源。不为了一条好评论选择内容跑题的来源。
- `news` 优先选择贴合新闻内容和分享角度的评论；`fun` 优先选择好玩、能接住笑点或反差的评论。
- 没有合适的真实评论时可以生成评论，但必须明确标为“我的评论”。
- 真实评论和生成评论不能混淆。
- 分享候选在补搜完成后统一生成一次，避免重复分享。

定时热榜进程把新生成的分享批次交给平台无关的分享分发器。分发器使用最终分选择和排序内容、维护每个目标的普通消息额度、在滚动时间窗口内控制总数和最小发送间隔，并在新批次到达时淘汰上一批尚未发送的普通消息，避免积压旧闻。即时阈值只与大众分比较，因此兴趣高分仍属于普通分享；大众 4.0 分代表应立即分享的重大内容，不受普通消息的时间窗口、条数和最小间隔限制，也不消耗普通额度。

具体 IM 平台只负责传输已经编排和渲染好的消息，不读取分享批次，也不判断评分或维护限流状态。当前 AstrBot transport 使用 AstrBot OpenAPI 把消息转发到配置的 IM 会话；增加其他平台时复用同一分享分发器，不复制分享策略和持久状态。

分享任务直接写入同一 SQLite 数据库，并冻结实际发送所需的 payload；review 批次文件不参与任务恢复。重启时继续调度尚未过期的等待任务，发送中断的任务标为结果不确定且不自动重发，并暂时占用普通额度，避免同一条消息重复出现在 IM 会话中。

具体调用参数、批次文件和统计字段见[拉取并学习](usage.md#拉取并学习)。
