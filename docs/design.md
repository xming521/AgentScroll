# AgentScroll 系统设计与内容规则

本文描述 AgentScroll 如何把互联网内容转化为可供 AI 学习和分享的信息，以及支撑这些流程的系统边界和平台采集方式。配置、接口、字段、平台支持与测试命令见[使用与接口](usage.md)。

## 业务目标

AgentScroll 让 AI 持续了解近期真实发生的热点、新闻、知识和网络表达，用于后续对话中的背景认知和即时分享。业务判断同时考虑：

- 真实性：知识、新闻来自实际读取的正文或评论。
- 趣味性：优先保留值得聊、好玩、抽象或能体现网络语境的内容。
- 成本：限制候选量、正文规模、模型调用次数、模型发送上下文大小，适应高频定时执行。

当前有两条主要入口：围绕指定主题主动搜索，以及从热榜中筛选值得学习的内容。

## 技术边界

### 模块依赖

依赖方向保持单向：collector 不依赖模型运行时，prompts 不执行 I/O，workflows 可以组合 collector 与 inference。

中文相关性排序使用 `jieba` 分词和词性；仅在分词没有共同词时使用字符 bigram 兜底。

### 推理代码维护

`agentscroll/inference/` 是从 WeClone 推理模块同步到本仓库的源码快照，使用 AgentScroll 不需要额外克隆 WeClone。

同步由 `.github/workflows/sync-weclone-inference.yml` 负责，只在 GitHub Actions 中手动触发。`__init__.py`、`audit.py` 和 `llm_client.py` 是本仓库保留的通用推理基础设施覆盖层，`online_infer.py` 不再同步；其余文件检测到上游变化时更新快照并创建 PR。

### 运行产物

| 目录 | 内容 |
| --- | --- |
| `outputs/hotlists/` | 热榜 JSON 快照、标题 TXT 和近期事件历史 |
| `outputs/knowledge/` | 搜索知识文件和热点知识卡 |
| `outputs/shares/` | 即时分享队列 |
| `outputs/logs/` | 运行与推理日志 |
| `outputs/test_artifacts/` | 真实平台测试证据 |

数据转换默认创建新文件，不覆盖输入；同一批次的关联产物使用一致名称，避免 JSON、TXT 和分享结果错配。

## 目标处理链路

目标链路为：信息源 → 采集 → 统一格式 → 持久化 → 去重、聚类与时序统计 → 兴趣过滤、打分与 Top-K → 补充正文、评论和相关报道 → LLM 分析与汇总 → Briefing 或推送。

其中聚类、完整兴趣建模、日报和推送属于后续设计方向，不能仅凭本图视为当前已经实现。当前公开行为以以下两条流程和[使用与接口](usage.md)为准。

## 主动搜索

### 场景路由

主题搜索支持三种场景：

- `formal`：面向公告、政策、报告、研究、新闻进展和正式分析，优先使用知乎、微信公众号和今日头条。
- `informal`：面向网络梗、流行语、二创、吐槽和评论区语境，优先使用微博、小红书、B站和抖音。
- `auto`：根据查询意图选择路线；没有明显信号的短主题词优先发现非正式语境，较长且信息明确的查询优先走正式场景。

用户显式指定平台时，以指定平台为准，不再应用默认场景路由。“正式”和“非正式”描述内容形态，不代表来源可信度；自媒体内容、未确认消息和网友说法仍需保留来源限定。

### 搜索规模

`quick`、`default` 和 `deep` 分别把每个平台的候选上限设为 5、10 和 20。B站对应最多搜索一、二、三页；小红书在 `quick` 模式使用公开索引发现候选，在 `default` 和 `deep` 模式优先使用 Playwright。其他平台沿用各自采集路径并按档位调整候选规模。

无论选择哪一档，命中的候选都会继续读取正文和评论。同一平台的详情请求按配置区间限速，不同平台可以并发。

### 内容读取

搜索结果只是候选入口。候选必须继续读取详情，获得真实正文或发布文案；需要评论时还要读取真实评论。

只有摘要、正文为空、正文过短或缺少有效原文地址的候选不进入最终知识。视频平台的正文指发布者文案或完整简介，不包含自动推断的字幕和音视频转写。微信公众号无留言访问权限时标记为受阻，不能记作没有留言。

微博、小红书、B站、抖音、微信公众号和今日头条只保留成功读取到正文或发布文案的条目。统一详情校验要求正文去除首尾空白后至少有 2 个字符，并且正文类型、解析来源和正文地址有效；详情受阻、只有摘要或正文为空的候选会被丢弃。微信公众号和今日头条使用通用文章提取器时，可识别的正文块至少需要 40 个字符；未命中正文块时，段落兜底结果至少需要 80 个字符。知乎文章和回答的详情正文少于 20 个字符时视为不可读。原始条目按配置上限保留有文字的评论，且不保存评论作者。

### 平台采集路径

以下描述的是当前代码中的读取路径，不等同于本轮已经验证平台在线可用：

- 微博：`mcp-server-weibo` 获取访客 Cookie；正文通过 MCP 单帖详情读取，评论通过微博评论 API 读取。
- 小红书：Playwright/XHR 与站外 URL 发现；正文优先读取页面初始状态中的笔记描述，专用正文 DOM 作为后备；评论从详情页签名响应提取。
- B站：公开搜索 API 与 Playwright 兜底；视频详情 API 读取完整简介，reply API 读取评论。
- 知乎：站外发现公开 URL，随后用 Playwright 读取正文，并按内容类型访问评论 API。
- 抖音：Playwright 与站外 URL 发现；正文读取分享页路由数据，专用正文 DOM 作为后备；评论从移动分享评论 API 提取。公开分享页出现 WAF challenge 时使用移动 Chromium 完成挑战并读取路由数据，不退回到 meta description。
- 微信公众号：搜狗微信搜索后访问文章页；只有文章声明留言区且具备访问权限时读取精选留言。
- 今日头条：服务端搜索页、热榜与站外 URL 发现；正文来自移动详情页或来源页，评论来自文章页签名响应。

### 知识沉淀

一次搜索把不同平台的有效内容合并成一份可追溯元数据和一份面向模型的紧凑知识文本。

- 每条内容保留平台、发布时间、正文、原文 URL、非零互动量和最多 10 个标签。
- 正文按配置上限保留；换行压缩为空格，超长内容按段落或句子边界截断并标明原始字符数。
- 评论去重后按点赞数降序保留最多 10 条；同赞数保持平台原顺序。
- 已知发布时间的内容按时间升序排列；无法确定时间的内容放在已知日期内容之前。
- 作者、平台内部 ID、图片、相关性解释、抓取状态、解析路径和 DOM 证据不写入 TXT。
- 正文为空或没有有效原文 URL 的条目不进入知识文件；微博的“图片评论”“转发微博”等无正文占位评论会被过滤。

具体文件、返回字段和可调上限见[返回值与知识文件](usage.md#返回值与知识文件)。

## 热榜学习

### 拉取与去重

热榜按业务类别组织。Agent 没有指定类别时使用“综合”组，依次包含微博、虎扑、百度贴吧和知乎。

拉榜阶段只生成索引，不读取正文或评论。不同榜单合并后按 Source ID 和榜单排名保留最先出现的条目，再按 URL 或标题全局去重。URL 规范化会统一协议和域名大小写、移除 fragment 并保留 query；标题规范化会统一 Unicode 兼容字符、大小写和连续空白。完整平台目录、Source ID 和快照格式见[NewsNow 热榜](usage.md#newsnow-热榜)。

### 第一轮筛选

模型只依据当前热榜快照选择值得继续处理的话题，不在第一轮打开 URL 或搜索互联网。目标分为：

- `news`：刚发生或正在发展，并具有现实公共价值、可能影响较多人的新闻与变化。
- `fun`：新词、固定表达、梗、反差、抽象或具有即时分享价值的内容。

最多选择 15 个话题，实际数量由符合条件的话题决定，不要求 `news` 与 `fun` 的数量均衡。筛选前先按标题规范化规则排除近期已经忽略或已归入事件的完全相同标题；若没有新标题则跳过模型请求并正常返回空话题。候选保留其在当前热榜中的整数 ID；模型只返回 ID，程序校验后再映射回标题和来源。属于同一事件的多个标题合并为一个代表话题，避免重复占用名额。

跨批次事件判断不额外生成摘要或 signature。程序先用 `jieba` 词性分词对标题做本地匹配，名词、人名、地名和机构名等名词类词权重更高；没有共同词时才用字符 bigram 兜底。若当前标题与最近 6 小时的历史标题包含相同明确人物名，即使普通标题相似度未达到召回阈值，也把该历史事件作为疑似候选并优先排列，但不据此直接判定为同一事件。每个当前标题最多召回 3 个历史事件候选，不对所有召回标题的合计字符数设置额外上限。现有第一轮模型请求同时把候选判断为 `new`、有实质进展的 `update` 或没有实质进展的 `seen`：`seen` 不进入采集，`new` 和 `update` 继续生成知识卡。仅人物、地点或主题相同不足以认定为同一事件，无法确认时按 `new` 处理。

上述状态统一保存在热榜快照目录的 `hotlist_history.json`。未选标题和模型确认的 `seen` 在第一轮成功校验后写入；`new` 只有在新知识卡批次落盘后才创建事件，`update` 只有在原卡成功改写或本次失败状态确定后才更新事件记录。事件保存本轮代表标题、关联标题、知识卡标题和证据原始标题，并始终指向同一张当前有效卡片。

标题筛选完成后立即保存独立 JSON，再进入正文采集；因此后续采集或知识卡生成失败时，仍可检查本轮选中的代表标题、平台、类别和关联标题。

模型先从当前热榜标题中找出属于同一事件的条目，并保留模型选出的代表标题用于描述本轮话题。正文采集独立选择非知乎入口；只有整组标题全部来自知乎时，卡片阶段才用一次批量模型请求把该组标题转换成 2 至 3 个短检索词，再到微博搜索具体帖子。系统不读取知乎正文或地址，知乎标题只作为待验证的话题线索，不能单独支持知识卡或分享。

程序默认以取得 3 个可读入口为目标，先尝试模型已识别的非知乎关联条目；不足时，纯知乎话题使用上述检索词，其他话题直接复用已有非知乎标题，仅到微博补采。虎扑和贴吧仍沿已有非知乎热榜入口下钻。最终只保留热榜快照日期及其之前连续 7 个自然日内、发布时间能够确认的帖子，同一帖子被多个检索词命中时只保留一次。某个入口失败、日期缺失或超出范围时继续尝试后续入口；微博补采后仍不足 3 条，则不直接成卡，最后才转入有限主动搜索。
仅有热榜标题、搜索摘要或失效地址时，不把话题标记为证据完整。

采集选中内容时，微博通过 `mcp-server-weibo` 定位 feed；虎扑读取帖子结构化数据；贴吧通过话题页和 Playwright 读取帖子与楼层；显式选择 Bilibili 热榜时，通过热搜标题定位视频并读取简介和评论。

### 知识卡与补搜

每个话题分别请求模型完成材料判断、知识卡生成和分享编排；多个话题并发处理，结果按话题 ID 汇总，新事件合并为本轮批次，更新事件写回原卡。单个话题请求失败或返回结果未通过校验时，该话题保留为 `needs_research` 并记录错误，不中断其他话题的生成、合并和落盘。知识卡模拟真人对近期谈资的简短记忆，只保留“有这么个事或梗”、大致意思和一至两个值得记住的信息点，不整理完整报道。每次请求使用共同的状态、评分、输出和来源规则，再只附加当前 `news` 或 `fun` 类别的专用判断与写作规则：

- `complete`：现有证据足以辨认基本事件或梗；即使精确数字、完整经过或各方回应不全，也可保留来源限定后生成简短知识卡。
- `needs_research`：未达到正文采集目标，或连基本事件、梗或有趣之处都无法辨认，需要有限补搜。
- `rejected`：证据已能确认话题是旧闻回顾、没有近期具体进展、不具现实公共价值、已经过时或与标题不符；不生成知识内容，也不进入分享和补搜。

`new` 生成新卡；`update` 的模型输入只补充原卡的标题、知识、聊天语境和上次更新摘要。更新证据明确支持新进展时，程序改写原卡中可能过时的当前概括，并替换单个 `latest_update`；不新建卡片，也不累积更新列表。首轮没有证明新进展时进入补搜，补搜后仍只有旧内容则淘汰本次更新，原卡保持不变。

补搜只处理 `needs_research`，复用 `agentscroll search` 的平台采集入口读取真实正文和评论：`news` 搜微博、微信公众号和今日头条，`fun` 搜微博和小红书，每个话题合计最多保留 3 条可读内容。3 条限额在详情和评论请求前按平台顺序尽量均分，因此 `news` 为 1/1/1，`fun` 为 2/1；这是由固定平台数和总限额直接计算的规则。多个补搜话题并发处理，不重新处理 `complete` 或 `rejected`，不直接使用 Bing、DuckDuckGo 摘要，也不启用 Codex 原生 Web Search。补搜只需让人知道话题大致在说什么，不做穷尽式事实核验；未确认新闻或指控必须保留“网传”“帖子称”等限定。

### 即时分享

模型按现有材料为每个话题给出 1 至 4 的即时分享评分，最多保留一位小数，综合考虑时效性、公共影响或趣味性，以及是否容易引发聊天回应。非 `complete` 状态或没有可用来源时评为 0 分；程序只将达到 3 分的话题放入分享队列。

分享队列 JSON 保留评分；实际分享文本包含大致内容或标题、真实原文地址和一条评论。`news` 生成能让人理解大致内容、同时想点开原文了解细节的分享文案；`fun` 直接使用原标题，不改写或补充分享文案，原标题单独看不够好玩或无法理解时不进入分享队列。两类都不伪造悬念或隐去改变内容性质的关键事实：

- 模型选择真实评论时只返回当前话题内唯一的本地评论 ID，由程序从证据回填；评论可以来自该话题的任一已采集帖子，不要求属于分享来源。
- `news` 优先选择已提供内容最直接、完整地支持分享文案和最新进展的来源；`fun` 优先选择已提供内容最能呈现笑点、反差或抽象内容的来源。不为了一条好评论选择内容跑题的来源。
- `news` 优先选择贴合新闻内容和分享角度的评论；`fun` 优先选择好玩、能接住笑点或反差的评论。
- 没有合适的真实评论时可以生成评论，但必须明确标为“我的评论”。
- 真实评论和生成评论不能混淆。
- 分享队列在补搜完成后统一保存一次，避免重复分享。

具体调用参数、批次文件和统计字段见[拉取并学习](usage.md#拉取并学习)。
